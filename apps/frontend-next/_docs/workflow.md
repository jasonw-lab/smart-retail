# AI 駆動・機能単位の開発ワークフロー

## 目的と適用範囲

Vue / React の frontend、Java / Go の backend に共通する進め方を定める。人間は要件・アーキテクチャ方針・最終 UI を確認し、AI が設計案、実装、別 AI のレビュー、検証、記録更新を担当する。毎回のコードレビューを人間へ戻さず、承認済み範囲で小さな機能を継続的に完成させる。

本リポジトリの実行コマンドは Next.js 版に限定する。Vue / Java / Go のパス・コマンド・CI は、対象リポジトリの AGENTS.md と実ファイルを確認して機能設計メモに記録する。言語名だけでコマンドを推測しない。

- issue の正本: `_docs/issues.html`（内容・依存関係・対応状態）
- 契約の参照: `_docs/adr/ADR-011-backward-compatible-retail-api-evolution.md`、`_docs/api-modifications.html`
- 運用の参照: `AGENTS.md`、`~/ai-rules/ai-common.md`
- ADR-011 は現時点で Proposed。文書の存在を承認と見なさず、初回の設計方針確認で適用範囲・承認を記録する。既存 Vue 契約を破壊しない方針は継続する。

## 1. 人間の確認は原則 3 点

確認は機能ごとではなく、関連 issue をまとめた開発単位でもよい。AI は確認に必要な成果物と推奨案を用意してから依頼する。既存の承認範囲は引き継ぎ、同じ判断を再確認しない。

| 確認点            | AI が用意する成果物                                                            | 人間が決めること                             | その後 AI に任せること                           |
| ----------------- | ------------------------------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------ |
| H1 要件           | 利用者・課題・対象/対象外・優先順位・画面案・受入条件・未決事項                | 何を作るか、業務上の正解、作業対象リポジトリ | 承認済み backlog から依存順で issue 選択、詳細化 |
| H2 アーキテクチャ | 構成図、API/データ責務、互換性、認証境界、代替案、移行/戻し方、AI 設計レビュー | 新規設計・重要変更の方針と許容範囲           | 方針内の機能設計、通常実装、修正、検証           |
| H3 最終 UI / 受入 | 起動手順またはプレビュー、主要操作の画面/動画、受入条件別の結果、既知制約      | 業務に合うか、操作性・見た目、最終受入       | 承認済み修正、完了記録、許可範囲の片付け         |

H2 は初回・方針変更時に実施し、既存パターンの機能追加では承認済み設計への参照で代替する。UI のない backend 変更は H3 で API の操作例・業務シナリオ結果を示す。

PR ごとの人間承認や手動 done 更新は標準工程にしない。ただしリポジトリ保護ルールは守る。自動マージを運用する場合は、H1/H2 で対象ブランチ・必要 CI・独立レビュー・許可範囲を明示し、設定を確認する。未設定なら AI はマージ可能な PR まで用意する。本書の追加だけでマージ・本番公開・他リポジトリの変更を許可したことにはならない。本番公開は既存の公開権限・手順に従う。

## 2. AI の役割と利用枠

役割はモデル名ではなく責務で分ける。GPT / Gemini / Claude / KIMI を交代可能とし、特定モデルの優劣や特定プランの無制限利用を前提にしない。

| 役割            | 責務                                                             | 初期の割当例（固定ではない）    |
| --------------- | ---------------------------------------------------------------- | ------------------------------- |
| 進行担当 AI     | issue 選択、依存管理、担当・ポート予約、受け渡し、統合、証跡確認 | GPT                             |
| 設計担当 AI     | 要件案、契約、変更範囲、受入条件・テストケース                   | Claude                          |
| 実装担当 AI     | 実装、テスト、mock、文書同期、指摘修正                           | KIMI または Gemini              |
| レビュー担当 AI | 要件・契約と差分の照合、欠陥の根拠提示、修正再確認               | GPT または設計/実装と異なる系統 |

設計レビューは設計者と、実装レビューは実装者と別系統のモデルにする。同じモデルの別セッションや自己点検は、独立レビューの代替としない。設計者による実装確認は補助として利用できるが、設計の誤りを見つける独立レビューは別に残す。

月額プランは利用可能な各製品のセッションで使う運用を基本とする。API 接続や無人のモデル間連携が利用できるとは仮定しない。連携手段が未整備なら、人間の操作は成果物パスと開始指示の受け渡しに限定する。API 利用・追加課金を必要とする仕組みは別途判断する。

利用上限に達したら現在の SHA・未完了事項・再開手順を保存し、利用可能な別系統へ交代する。独立レビュー担当が確保できなければ review 待ちとし、レビューを省略して完了させない。各開発単位で手戻り、レビューの有効指摘、利用上限待ち時間を振り返り、次回の割当を調整する。

## 3. 変更規模に応じたレビュー

| 種別                                             | 設計成果物                               | AI レビュー                              | 人間の追加確認                                    |
| ------------------------------------------------ | ---------------------------------------- | ---------------------------------------- | ------------------------------------------------- |
| 小: 文言・既存パターン・契約変更なし             | issue 内の対象/受入条件/検証手順で代替可 | 独立した実装レビュー 1 回                | 原則不要。UI 変更は H3 にまとめる                 |
| 通常: 新規画面・後方互換 API 追加                | 機能設計メモ                             | 設計レビュー + 実装レビュー              | H1/H2 の範囲を超える場合のみ                      |
| 重要: 認証境界・破壊的契約・データ移行・新規基盤 | 機能設計メモ + ADR/移行計画              | 設計/実装レビュー + 別観点の横断レビュー | H2 で変更方針を確認。承認後の通常修正は AI が続行 |

受入条件から正常系・異常系・権限・互換性のテストケースを設計時に定義する。実装者がテストを書いてよいが、レビュー者はケース漏れ、assertion の弱体化、mock と実 API の不一致も確認する。AI 同士の合意だけでは品質ゲートを通過しない。

## 4. 成果物による受け渡し

通常以上の issue は `_docs/plan/feature-<issue-id>.md` に以下をまとめる。進行担当が状態を更新し、同時編集を避ける。

- issue、目的、対象外、H1/H2 の承認記録または参照、未決事項
- frontend/backend の対象リポジトリ、base/作業ブランチ、worktree、担当モデル/セッション
- 依存 issue、変更対象ファイル、API の request/response・型の before/after、mapper・validation・互換性
- 受入条件 ID と対応するテストケース、testid、mock 更新箇所、実 backend との確認方法
- 実行コマンド、必要環境、予約ポート、CI の必須 job、統合順序、移行/戻し方
- レビュー対象の base SHA/head SHA、レビュー記録、検証 SHA・日時・結果・ログ/CI URL、未実行項目
- 次の担当への再開手順、残課題、人間確認の対象版と結果

レビュー者には設計メモ、対象 SHA 間の diff、worktree/PR を渡す。実装者の説明だけに依存せず正本とコードを読む。指摘は `_review/review_<MMDD>_<issue-id>.<agent>.md` に対象・行/機能・日付・レビュアー・全体評価・重大度・根拠・推奨対応を記録する。

対応表には指摘 ID、修正/見送り理由、修正 SHA、再検証結果、レビュー者の再確認を追記する。High は修正またはレビュー者が根拠を確認して撤回する。実装者だけで「対応不要」にしない。Medium/Low の延期は影響・追跡 issue を残し、受入条件や安全性に影響する場合は完了を止める。レビュー後の変更は該当差分を再レビューし、最終 SHA でゲートを確認する。

## 5. 機能ごとの進行フロー

| 順序 | 担当            | 作業と通過条件                                                                                |
| ---- | --------------- | --------------------------------------------------------------------------------------------- |
| 1    | 進行 AI + 人間  | 要件案をまとめ H1。承認済み backlog の依存順で対象を選ぶ                                      |
| 2    | 設計 AI → 別 AI | 機能設計・テストケース作成、独立設計レビュー。必要時 H2                                       |
| 3    | 進行 AI         | 対象 repo/base を確認、issue ごとに worktree とポートを予約                                   |
| 4    | 実装 AI         | Backend 対象なら、旧契約を固定するテスト → 実装 → backend ゲート。契約・OpenAPI・設計書を同期 |
| 5    | 実装 AI         | Frontend の UI 項目、型、API client、mapper、Zod、mock を整合し対象 spec を検証               |
| 6    | 別 AI → 実装 AI | 実装レビュー → 指摘修正 → 再確認。重要変更は横断レビューも実施                                |
| 7    | 進行 AI         | 機能ゲート、PR 作成、対象 revision の必須 CI job が成功したことを確認                         |
| 8    | 進行 AI         | 依存順に 1 機能ずつ統合し、統合結果で全件 E2E。成功後に次を統合                               |
| 9    | 進行 AI + 人間  | 統合済み成果物をまとめ H3。指摘は同じループで修正し影響範囲を再検証                           |
| 10   | 進行 AI         | DoD を照合して issues.html・サマリー・更新日・履歴、api-modifications.html を更新し片付け     |

Frontend のみなら手順 4 は対象外。Backend 変更は対象 repo への明示指示または許可された PR 作成の範囲で行い、未許可なら frontend の準備と必要差分の記録まで進める。

本プロジェクトの既存統合 base は frontend `feat/retail-api-integration`、backend `feature/agent`。開始時に存在と採用状況を確認する。新規作業ブランチの既定は `codex/<issue-id>-<topic>`。既存の未コミット変更を移動・破棄しない。

## 6. 検証ゲートと統合

Next.js の機能ゲートは `pnpm lint`、`pnpm format:check`、`pnpm typecheck`、`pnpm build`、対象 spec の `pnpm test:e2e e2e/specs/<対象>.spec.ts`。pre-commit は staged ファイルだけを対象とするため全体ゲートの代替にしない。型チェックが生成型に依存する場合は先に build して再実行する。

PR Check は全 base の PR を対象とし、`lint-and-typecheck`、`build`、`e2e` を確認する。GitHub の必須チェック設定は別途必要であり、YAML の変更だけでマージを強制的に防げるわけではない。未実行・失敗・キャンセル・必要 job の skip は成功扱いにしない。ローカル成功だけで CI 成功を宣言しない。

Vue/Java/Go は各 repo の規定ゲートを使う。共有 API の変更では利用中の frontend ごとの互換テストを含める。Next.js の mock E2E は実 backend との接続検証を代替しない。Backend を変更する issue は backend ゲートに加え、実 backend 接続で対象操作を確認し、使用した両 repo の SHA を記録する。

統合は直前の green SHA に 1 機能ずつ追加し、各統合結果に全件 `pnpm test:e2e` を実行する。PR CI が同一の統合内容を検証済みなら証跡を再利用できるが、base 更新後の古い成功は再利用しない。失敗時は以降の統合を止め、直前 green との差分から原因を調査する。全件実行時間が問題になったら実測に基づき運用を改訂し、無断でゲートを削らない。

VRT は承認済み UI 変更に対応する差分だけ更新可能。別 AI が before/after と要件の対応を確認し、H3 の確認資料に含める。原因不明の差分を一括採用しない。テストの skip/fixme や期待値の緩和で通過させない。

## 7. worktree・ポート・中断

1 issue につき 1 worktree、同時書込担当は 1 AI。レビュー者は読み取り専用で確認し、交代時は差分と所有者を引き継ぐ。frontend/backend にまたがる場合は各 repo に専用 worktree を持つ。統合・正本更新は進行担当が直列に行う。

ポートはホスト上の進行担当が空きスロット N（1〜99）を予約し、機能設計メモにホスト・worktree・所有者と記録する。別プロジェクトも含め使用中のスロットを重複予約しない。

| スロット | E2E_PORT = 3100 + N | MOCK_PORT = 8100 + N |
| -------- | ------------------- | -------------------- |
| 1        | 3101                | 8101                 |
| 2        | 3102                | 8102                 |
| 3        | 3103                | 8103                 |

ルート Playwright 設定は process.env を読むため、`.env.local` に書くだけでは割当を保証しない。例えば `CI=true E2E_PORT=3101 MOCK_PORT=8101 pnpm test:e2e e2e/specs/products.spec.ts` と明示する。現行設定は CI=true で既存サーバー再利用を無効化する。開始前にもポート占有を確認し、使用中なら他人のプロセスを停止せず別スロットを予約する。同一 worktree の build/E2E は直列実行する。

完了後は未コミット/未追跡ファイルがないこと、必要なコミットが統合先に保存済みであること、他セッションが使用していないことを確認して `git worktree remove <path>` と不要なローカルブランチの `git branch -d <branch>` を行う。強制削除しない。リモートブランチ削除は既存運用に従う。

中断は状態・差分・再開手順を保存してポートを解放する。破棄が決まった場合も未統合成果物を退避し、issue に理由を記録してから片付ける。単に done と記載されているだけでは削除しない。

## 8. AI で解決する範囲と例外

仕様内の不具合、通常のテスト失敗、レビュー指摘は AI 同士で修正する。同じ原因不明の失敗が 2 回続いたら別 AI に調査を交代し、再現条件とログを残す。それでも解決できない場合は、試したこと・未確認範囲・必要な判断だけを人間へまとめる。

Docker などが使えなければ、まず既存 CI または実行可能な別 AI 環境へ検証を引き継ぐ。引き継ぎ先がなければ検証待ちとし、実行コマンド・対象 SHA・必要環境を記録して環境提供を依頼する。未実行を成功にせず、独立して進められる文書整備や別 issue は続ける。

人間へ戻すのは、業務要件の矛盾、承認範囲を超える設計/互換性/認証境界の変更、データ喪失を伴う判断、必要な権限・環境・費用の不足、H3 の業務判断。影響する作業だけを保留し、選択肢と推奨案を用意する。

## 9. 完了定義（DoD）

- H1/H2 の必要な確認が記録され、受入条件が満たされている。
- 独立 AI レビュー記録があり、High が解消、その他の扱いが確定している。
- 最終変更に対する機能ゲート・必須 CI と統合結果の全件 E2E が成功している。
- Backend 対象なら backend ゲート、旧 Vue 契約の回帰、実 backend 接続確認が成功している。
- 契約、OpenAPI、型、mock、関連設計書、api-modifications.html が対象変更と同期している。
- H3 で対象版を受入済み。UI/API が変わる追加修正は再確認済み。
- AI が証跡を照合し issues.html の状態・サマリー・最終更新日・更新履歴を同期している。

実装済み・レビュー待ち・CI 待ち・統合待ち・受入待ちは done にしない。正本に専用状態がなければ既存の未完了状態の詳細欄に待ち理由を記録する。
