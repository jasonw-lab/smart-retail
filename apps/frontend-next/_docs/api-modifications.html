UI-first API 項目整合レポート

生成日: 2026-07-14  |  対象ブランチ: feat/retail-api-integration  |  分析対象: 19 ドメイン（products / stores / devices / inventory / transactions / alerts / dashboard / categories / payments / heartbeat / ai-alerts / system/*）
スコープ方針: 今回の作業では UI の項目・フィルタ・フォームを正として、frontend 側の型/API クライアントを整合させます。 smart-dx-backend のコード自体は修正しませんが、Backend 側で対応が必要な項目は「Backend 要修正」として明記し、 別途 backend 改修タスクの入力資料として利用します。

18Frontend 要修正
7Backend 要修正
3両方要修正
Frontend UI コンポーネント / 型 / API クライアントの修正のみ Backend Backend API スキーマ・エンドポイントの追加が必要 両方 Frontend 型を先に整え、Backend 対応後に完全稼働 Document 現状のマッピングを文書化・監視
機能 UI 項目 現在の API 状況 提案する修正 対象側 理由
products imageUrl Product.imageUrl は存在するが、productFormSchema / ProductForm に存在しない 対応済み（2026-07-19 コード確認で実装済み）。productFormSchema / ProductForm に imageUrl 入力欄が存在 Frontend 一覧でサムネイルを表示しているが、入力・編集 UI がなくデータが埋められない
products status ProductForm の defaultValues で status=1 を暗黙設定。入力欄なし 対応済み（2026-07-19 コード確認で実装済み）。ProductForm にステータス切替（有効/無効）が存在 Frontend ユーザーが意図的に無効化できない。schema には既に定義済み
products productCode (更新時) 編集時は disabled だが updateProduct.mutateAsync(values) で送信。UpdateProductDto には存在しない 対応済み（2026-07-19 コード確認で実装済み）。更新送信前に productCode を omit 済み Frontend 編集不可コードを誤って送信するとバックエンドで無視/エラーになりうる
products categoryId フィルタ フィルタは数値 ID 1〜5 のハードコード。Category API は存在する 対応済み（2026-07-19 コード確認で実装済み）。useCategories() による動的選択肢を使用 Frontend カテゴリ追加時にフィルタが陳腐化する。API からの動的選択が正しい
products productCode / status フィルタ ProductQuery は productCode/status をサポートするが UI にない 現状維持（未使用 API フィルタを文書化） Document 現 UI では不要。将来必要になったら追加可能
stores address フィルタ UI では address 入力欄あり・URL も書き換えるが、page.tsx と API クライアントが受け渡していない 対応済み（2026-07-19 コード確認で実装済み）。UI → URL → page.tsx → StoreQuery → client/server getPage まで接続済み（実 Backend の address 受付は backend 側で要確認） Frontend フィルタ UI が機能していない。SSR リロード時も値が落ちる
stores businessHours / manager / todaySales / alertCount / highestAlertPriority Store 型に存在。テーブル表示のみ 現状維持（表示専用フィールド） Document 作成・更新フォームでは編集しないダッシュボード系計算値
devices metadataJson DeviceForm は文字列入力、API は metadata: Record<string, unknown> 現状の JSON.parse/stringify 変換を維持。mapper 切り出しを推奨 Document UI 上の中間表現と API 表現の違い。型を揃える必要なし
devices URL params name/type/page URL 短縮形と API クエリ名が異なるが page.tsx でマッピング済み 現状維持。URL と API のマッピングをコメントで明記 Document ユーザー体験上短縮形は妥当。内部的に整合している
inventory turnoverRate 在庫回転率サマリーカードは UI 上 null でハードコード 対応済み（ISSUE-001）。Backend は summaries の turnoverRate を null で返し、frontend 型は number | null、UI は `-` 表示を維持 両方 計算式が業務上確定するまで null 固定（ADR-011 §2/§6）。実計算は別途 ADR で扱う
inventory Dispose reason 廃棄ダイアログで reason 選択あり。DisposeDto / InventoryTransaction に reason フィールドがない 対応済み（ISSUE-001）。廃棄は POST /retail/inventories/{lotId}/discard の {quantity, reason, remarks} 契約へ切替。outbound への note 埋め込みは廃止 両方 Backend が数量減算と reason 付き DISPOSAL 履歴を同一トランザクションで登録する（ADR-011 §2）
inventory status enum Frontend: OUT_OF_STOCK/EXPIRING/OVERSTOCK、Backend: LOW_STOCK/EXPIRY_SOON/HIGH_STOCK frontendToBackendStatus/backendToFrontendStatus マッパーを維持 Document 既存マッパーで動作。どちらを正とするかは別途調整検討
inventory inventoryId (dispose) dispose API で lotId を inventoryId として送信 対応済み（ISSUE-001）。inventoryId は一貫してロット単位の在庫レコード ID（lots[].id）と確定。集約行は数値 id を持たず summaryKey で識別 Backend ADR-011 §2 で語義を固定。discard エンドポイントも {inventoryId}=ロット ID で実装済み
inventory remarks vs note 在庫作成は remarks、補充/廃棄は note で同概念が別名 現状維持。ドメインごとに用語が分かれていることを文書化 Document 各 DTO の責務が異なる。統一は任意
inventory list response format Backend 本来の契約はロット単位 raw 配列。UI・E2E は SKU 集約形式（lots プロパティ付き）を期待 対応済み（ISSUE-001）。集約専用の GET /retail/inventory-summaries を追加し、/retail/inventories はロット単位契約を維持。
frontend は summaries を利用しクライアント側でページング。E2E mock もロット正本＋summaries 導出に修正 		両方 ADR-011 §2 の追加型拡張で解決。集約行の識別は summaryKey、ロット操作は lots[].id を使用
transactions — 表示・フィルタ・詳細で使用する全フィールドが API 型に存在 現状維持 Document gap なし。売上作成フォーム UI が未実装であることのみ記録
alerts category UI は category フィルタ・表示あり。BackendAlertVO / GET クエリに category がない BackendAlertVO.category?: string と AlertQuery.category を追加。backend 対応後サーバフィルタ可能に 両方 現状は alertType から derive。backend が category を返せば正確な分類が可能
alerts priority / category / status クエリ alertApiClient.getList は storeId/status のみ送信。getPage はクライアント側フィルタ getList/getPage で priority / category / storeId / status を backend へ送信 両方 データ増加時にクライアント側フィルタはスケールしない
alerts read フラグ UI は read 状態を管理。BackendAlertVO / API に read がない BackendAlertVO.read?: boolean と PATCH /{id}/read エンドポイントを型として追加 両方 現状は status=acknowledged で代替。read と acknowledge のワークフロー分離が理想
alerts value 型の不一致 id/ deviceId/ storeId/ priority / status / createdAt で型・値セットが異なる normalizeBackendAlert マッパーを維持し、backend 統一時に削除予定で文書化 Document 現状マッパーで動作。backend 改修時に統一候補
dashboard weather WelcomeMessage に weather オブジェクトがあるがハードコード /retail/dashboard/weather エンドポイントを検討、または外部天気 API 連携 Backend 現状は静的値。今後動的にする場合 backend または外部 API が必要
dashboard userName / avatarUrl Dashboard API ではなく /users/me から取得 現状維持（アーキテクチャ上妥当） Document ダッシュボードドメイン外の認証情報。依存関係を明記
categories — 専用 UI が未実装。product から categoryId/categoryName を参照 categories 管理ページ追加時は既存 API 型でカバー可能 Document API 型は整備済み。product の categoryId 入力をセレクト化する価値あり
payments totalAmount / details.subtotal / details.id payments 専用 UI がなく、PaymentPayload は amount / details（id/subtotal なし） payments 管理 UI 追加時に PaymentPayload を CreateSalesDto と整合させる Backend 現状 payments API は利用箇所なし。将来 UI 実装時に backend 契約調整が必要
heartbeat lastHeartbeat / errorCode Device 型/UpdateDeviceDto に存在。heartbeat 送信 UI は未実装 現状維持 Document device 管理 UI で表示・編集可能。heartbeat POST は自動化向け
system/user exportUsers で startTime/endTime UserQuery は日付範囲をサポートするが exportUsers では転送しない 対応済み（ISSUE-006）。exportUsers の startTime/endTime 転送に加え、Export ボタンへ exportUsers + Blob ダウンロードを接続 Frontend 日付フィルタがエクスポートに反映されない
system/user UserForm.password UserForm 型には password? があるが schema/UI にはない 対応済み（2026-07-19 コード確認で実装済み）。UserForm 型から password は削除済み Frontend 作成時もパスワード入力がない。backend が自動生成する前提なら型から除外
system/user ステータス列ラベル user-table-client のヘッダーが "En"、セルが "ye"/"no" 対応済み（2026-07-19 コード確認で実装済み）。ヘッダー Status、セル Active/Disabled に修正済み Frontend 明らかな表示崩れ
system/role status フィルタ role-table-client に Status ドロップダウンあり。RoleQuery / API 送信にない 対応済み（ISSUE-007）。client 側は接続済みのため、server getPage への status 付与・page.tsx の SearchParams 受け渡し・MSW mock のフィルタを追加 Frontend フィルタ UI が未接続
system/menu visible フィルタ menu-table-client に Status ドロップダウン（Visible/Hidden）あり。MenuQuery / API 送信にない 対応済み（2026-07-19 コード確認で実装済み）。MenuQuery・client・table・E2E mock まで接続済み Frontend フィルタ UI が未接続
system/menu params Menu/MenuForm に params 配列あり。UI 上入力欄なし 現状維持。backend がサポートする場合は dialog に追加 Document 使用実態が不明なため保留
system/dict status フィルタ dict-table-client に Status ドロップダウンあり。handleSearch で status を params に入れていない 対応済み（2026-07-19 コード確認で実装済み）。handleSearch で status を DictQuery に接続済み Frontend dictApiClient.getPage は status を既に送信可能。UI 接続のみ不足
system/dict Go to ページ入力 ページネーションの Go to 入力欄が onChange/Enter 未実装 対応済み（ISSUE-008）。Go to 入力を handlePageChange に接続（1〜totalPages にクランプ）。Next ボタンの onClick/disabled、ページ番号表示もあわせて修正 Frontend UI 部品はあるが機能していない
system/notice priority / level フォームは level（L/M/H）、一覧は priority（0/1/2）。NoticeForm に priority がない 対応済み（ISSUE-003 / ADR-011 §4）。Backend/Vue 版の level 契約に統一。数値 priority を廃止し作成・更新は level のみ送信、一覧も level ベースのラベル/badge に変更 両方 保存と表示で別フィールドを使うとデータ不整合の原因になる
system/notice type / targetType schema が z.number() 任意値を許容 schema を z.union([z.literal(1), z.literal(2)]) / literal(0/1) に絞る Frontend UI の選択肢と一致しない値を防ぐ
system/log module 円グラフ 円グラフが固定ラベル。table/badge は API 値（DICTIONARY/DEPT/MENU 等） 対応済み（2026-07-19 コード確認で実装済み）。moduleStats から円グラフ・凡例を動的生成済み。なお Avg. Response Time の固定モックは ISSUE-009 で除去 Frontend 固定データは実データと矛盾する可能性がある
system/config — UI 項目と API 型が一致 現状維持 Document gap なし
本レポートは features/ および app/[locale]/(dashboard)/ 下の UI コードと、 対応する API 型/クライアントを比較して生成しました。
Backend 要修正項目は smart-dx-backend 側の実装計画に利用してください。
