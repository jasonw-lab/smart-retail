    access_token失効後にrefresh_tokenが使われず再ログインになる

    High対応完了

    指摘内容

    access_token Cookieが消えるとrefresh_tokenが有効でもSSR経路で再ログインになっていた。

    対応理由

    業務画面で短時間離席後にセッション断になるとUXが大きく悪化し、refresh tokenを保持している設計意図とも矛盾するため。

    対応方法

    • middlewareで access_token が無く refresh_token がある場合、Backend refresh-token APIを呼ぶ。
    • Cookie再発行後、同一URLへredirectしてSSRが新tokenを参照できるようにした。

    主なCode修正

  return NextResponse.redirect(loginUrl);
}
    After

const refreshToken = request.cookies.get('refresh_token')?.value;

if (!accessToken && refreshToken) {
  const refreshed = await refreshAuthTokens(refreshToken);
  if (refreshed) {
    const response = NextResponse.redirect(request.nextUrl);
    setAuthCookies(response, refreshed);
    return response;
  }
}

  return NextResponse.redirect(loginUrl);

    proxy Route Handlerの401リトライでbody二重読取

    High対応完了

    指摘内容

    proxy Route Handlerの401リトライ設計では同じRequest bodyを複数回読む可能性があった。

    対応理由

    Request bodyは一度しか読めず、POST/PUT/PATCHのリトライやmultipart対応で破綻するため、転送前に一度だけ読む形へ寄せる必要があるため。

    対応方法

    • proxy側のbodyは arrayBuffer() で一度だけ読み、Backendへ透過。
    • Content-Type固定をやめ、元リクエストの Content-Type / Accept を転送。

    主なCode修正

    app/api/proxy/[...path]/route.tslib/api/result.ts_docs/adr/ADR-002-jwt-authentication.md

    主要なコード一部（修正前/修正後）

    Before
    async function fetchWithAuth(request: NextRequest) {
  const body = await request.text();
  return fetch(url, { method, body });
}

if (response.status === 401) {
  // Same request body is read again here.
  response = await fetchWithAuth(request);
}
    After
    const body =
  request.method === 'GET' || request.method === 'HEAD'
    ? undefined
    : await request.arrayBuffer();

const headers = new Headers();
copyHeader(request.headers, headers, 'content-type');
copyHeader(request.headers, headers, 'accept');

const response = await fetch(backendUrl, {
  method: request.method,
  headers,
  body,
  cache: 'no-store',
});

    並行401時のトークンリフレッシュ競合

    Medium対応済み確認

    指摘内容

    複数リクエストが同時に401になった場合のrefresh競合が設計上明確でなかった。

    対応理由

    refresh token rotationがある環境では多重refreshがセッション断を引き起こすため、single-flight前提を明確にする必要があるため。

    対応方法

    • Client fetch wrapperの refreshPromise / isRefreshing によるsingle-flightを確認。
    • ADR上の責務を「Route Handler refresh」ではなく「client側 single-flight」へ合わせて更新。

    主なCode/Doc修正

    lib/api/client.ts_docs/adr/ADR-002-jwt-authentication.md

    主要なコード一部（修正前/修正後）

    Before
    if (response.status === 401) {
  await fetch('/api/auth/refresh', { method: 'POST' });
  return fetchApi(path, options, true);
}
    After
    let isRefreshing = false;
let refreshPromise: Promise<boolean> | null = null;

if (response.status === 401 && !isRetry) {
  if (isRefreshing && refreshPromise) {
    const refreshed = await refreshPromise;
    if (refreshed) return fetchApi<T>(path, options, true);
  } else {
    isRefreshing = true;
    refreshPromise = refreshToken();
    try {
      const refreshed = await refreshPromise;
      if (refreshed) return fetchApi<T>(path, options, true);
    } finally {
      isRefreshing = false;
      refreshPromise = null;
    }
  }
}
